# สำรองและกู้คืนข้อมูล

> **สถานะ:** สร้างและทดลองกู้จริงแล้ว 7 ส.ค. 69

---

## 🔴 เรื่องที่ต้องรู้ก่อนอื่น

ตรวจระบบสำรองข้อมูลของผู้ให้บริการฐานข้อมูลแล้วพบว่า:

```
pitr_enabled: false      ← ย้อนเวลากลับไปจุดใดจุดหนึ่ง: ปิดอยู่
backups: []              ← ข้อมูลสำรองที่มีอยู่: ไม่มีเลยสักชุด
```

**แปลว่าตอนนี้ถ้าฐานข้อมูลเสีย หรือมีคนลบข้อมูลผิด ข้อมูลจะหายถาวร กู้ไม่ได้**

นี่ไม่ใช่ความเสี่ยงบนกระดาษ — วันเดียวกันนั้นเองมีการลบตัวแทน 4 สาขาออกจากระบบ
และไม่มีทางกู้กลับมาได้เลย เพราะไม่มีข้อมูลสำรองอยู่

เอกสารนำขึ้นระบบฉบับก่อนเขียนไว้ว่า "ผู้ให้บริการสำรองให้อัตโนมัติ" — **ข้อความนั้นไม่จริง**
แผนใช้งานปัจจุบันไม่ได้สำรองให้ จึงต้องมีระบบสำรองของเราเองที่ควบคุมได้และทดลองกู้ได้จริง

---

## ใช้งาน

```bash
npm run backup                        # สำรอง → backups/<วันเวลา>/
npm run restore backups/<โฟลเดอร์>     # ตรวจเทียบอย่างเดียว ไม่แตะฐานข้อมูล
npm run restore backups/<โฟลเดอร์> --apply --yes   # กู้คืนจริง
npm run backup:drill                  # ซ้อมกู้คืนทั้งวงจร (ไม่แตะข้อมูลจริง)
```

**ควรสำรองก่อนทุกครั้งที่จะ** รัน `npx supabase db push` · ลบตัวแทน/ผู้ใช้ · นำโค้ดชุดใหญ่ขึ้นระบบ

---

## ครอบคลุมแค่ไหน — ต้องรู้ให้ตรงกัน

| | สถานะ |
|---|---|
| ข้อมูลธุรกิจทั้งหมด 23 ตาราง (ตัวแทน ลูกค้า ลูกค้าเป้าหมาย ใบเสนอราคา การตั้งค่า บันทึกการใช้งาน) | ✅ ครบ |
| รายชื่อบัญชีผู้ใช้ (ใครมีบัญชีบ้าง อีเมล บทบาท สาขา) | ⚠️ ได้แค่รายชื่อ |
| **รหัสผ่านผู้ใช้** | ❌ **สำรองไม่ได้** |
| ไฟล์แนบที่อัปโหลด (รูป เอกสาร) | ❌ อยู่คนละที่กับฐานข้อมูล |

**ผลที่ตามมาถ้าต้องกู้ทั้งระบบจริง:** ข้อมูลกลับมาครบ แต่ **ทุกคนต้องตั้งรหัสผ่านใหม่**
ระบบยืนยันตัวตนไม่เปิดให้อ่านรหัสผ่านออกมา ใครก็สำรองไม่ได้ ไม่ใช่แค่เรา

🔒 **ไฟล์สำรองมีข้อมูลลูกค้าจริงและรหัสลับของตัวแทน** — ห้ามส่งต่อ ห้าม commit
(`backups/` ถูกกันไว้ใน `.gitignore` แล้ว)

## การกู้คืนทำงานแบบไหน

ใช้วิธี **"ทับของเดิมถ้ามี เพิ่มถ้าไม่มี"** — กู้เฉพาะสิ่งที่หาย ไม่ไปลบของใหม่ที่เกิดขึ้นหลังวันสำรอง

⚠️ แปลว่า**ไม่ใช่การย้อนเวลากลับ** — แถวที่ถูกลบไปจะกลับมา แต่แถวที่เพิ่มเข้ามาใหม่ยังอยู่
ซึ่งเป็นสิ่งที่ต้องการในกรณี "ลบผิด" (กรณีที่เกิดบ่อยที่สุด)

**โหมดตรวจเป็นค่าตั้งต้นเสมอ** — สั่ง `npm run restore <โฟลเดอร์>` เฉย ๆ จะไม่แตะฐานข้อมูล
แค่บอกว่าของในไฟล์กับในฐานข้อมูลต่างกันตรงไหน จะกู้จริงต้องพิมพ์ `--apply --yes` ยืนยัน

`rate_limits` ไม่ถูกกู้ทับโดยตั้งใจ — เป็นตัวนับกันยิงถี่ที่เปลี่ยนตลอดเวลา
เอาค่าเก่ามาทับเท่ากับรีเซ็ตตัวนับของคนที่กำลังถูกจำกัดอยู่

## ผลการซ้อมกู้คืน (7 ส.ค. 69)

**ระบบสำรองที่ไม่เคยทดลองกู้ ไม่นับว่ามีระบบสำรอง** — เคสที่เจอบ่อยที่สุดคือสำรองไว้ครบทุกวัน
แต่วันที่ต้องใช้จริงกลับกู้ไม่ได้ เพราะไม่มีใครเคยลอง

`npm run backup:drill` จำลอง "ลบข้อมูลผิด" ของจริงแล้วกู้กลับ ผลล่าสุด:

```
✅ สร้างข้อมูลทดสอบ
✅ สำรองข้อมูล — และข้อมูลทดสอบอยู่ในไฟล์จริง        รวม 9,725 แถว จาก 23 ตาราง
✅ ลบข้อมูลทิ้ง (จำลองการลบผิด) — ยืนยันว่าหายจริง
✅ สั่งกู้คืนจากไฟล์สำรอง
✅ ข้อมูลกลับมาครบถ้วนตรงทุกช่อง                     ตรวจครบ 28 ช่อง
✅ หลังกู้คืนแล้วยังบันทึกรายการใหม่ได้              ได้เลขใหม่ 9871 (ไม่ชนของเดิม)
✅ เก็บกวาดข้อมูลทดสอบและไฟล์ของการซ้อม
```

การซ้อมแตะเฉพาะข้อมูลที่ตัวเองสร้างขึ้นมา ไม่ยุ่งกับข้อมูลจริงแม้แต่แถวเดียว รันซ้ำได้ตลอด

### กับดักที่การซ้อมนี้จับได้ (และแก้ไปแล้ว)

บางตารางใช้เลขรันอัตโนมัติเป็นคีย์ เวลากู้เราใส่เลขเดิมกลับเข้าไป แต่ "ตัวนับ" ของฐานข้อมูลไม่ขยับตาม
→ **กู้เสร็จดูเรียบร้อยทุกอย่าง แต่พอมีการบันทึกรายการใหม่จะไม่ผ่านเลย** เพราะระบบขอเลขที่มีอยู่แล้ว

แก้ด้วย migration `0131_restore_sync_sequences.sql` ซึ่ง `restore.mjs` เรียกให้เองทุกครั้งหลังกู้
ขั้นตอนที่ 6 ของการซ้อมมีไว้ยืนยันข้อนี้โดยเฉพาะ

## สำรองอัตโนมัติรายวัน ✅ (ตั้งแล้ว 13 ส.ค. 69)

ตั้งเป็นงานตามเวลาของ Windows บนเครื่องนี้ — ทำงานทุกวันเวลา **02:00 น.**

| หัวข้อ | ค่า |
|---|---|
| ชื่องาน | `Benjamin PMS - สำรองข้อมูลรายวัน` |
| สคริปต์ | `scripts\backup-daily.cmd` |
| บันทึกผล | `backups\backup-daily.log` (ต่อท้ายทุกครั้ง — ย้อนดูได้ว่าวันไหนผ่าน/ไม่ผ่าน) |

สั่งรันเองได้ทันทีโดยไม่ต้องรอเวลา:
```
schtasks /Run /TN "Benjamin PMS - สำรองข้อมูลรายวัน"
```

**ข้อจำกัดที่ต้องรู้** — ทำงานเฉพาะตอนเครื่องนี้เปิด ถ้าปิดข้ามวัน วันนั้นจะไม่มีไฟล์สำรอง
(`npm run preflight` เตือนเองถ้าไฟล์ล่าสุดเก่าเกิน 7 วัน)

**กับดัก 2 ข้อที่เจอจริงตอนตั้ง** (เขียนไว้ในไฟล์ .cmd แล้ว ห้ามแก้ย้อน)
- ห้ามใส่คอมเมนต์ภาษาไทยในไฟล์ .cmd — cmd อ่านคำสั่งเพี้ยนแล้ว**ไม่ทำอะไรเลยแบบเงียบ ๆ** (log ว่าง ไม่มีไฟล์สำรองเกิดขึ้น)
- ห้ามเรียกผ่าน `npm run backup` — บนเครื่องนี้ npm ทิ้งรหัสข้อผิดพลาดค้างเป็น 1 ทั้งที่สำรองสำเร็จ ทำให้รายงานผลผิด · เรียก `node scripts\backup.mjs` ตรง ๆ แทน

## เก็บไฟล์สำรองไว้นอกเครื่อง (เครื่องมือพร้อมแล้ว 14 ส.ค. 69 — เหลือตั้งเอง 1 ครั้ง)

ตั้งตัวแปร `BACKUP_DIR` ชี้ไปโฟลเดอร์ที่ **ซิงก์ขึ้นคลาวด์อยู่แล้ว** เท่านี้ก็ถือว่าอยู่นอกเครื่อง
ไม่ต้องซื้อบริการเพิ่ม — เครื่องนี้มี OneDrive อยู่แล้ว

```powershell
setx BACKUP_DIR "C:\Users\boomb\OneDrive\benjamin-backups"
```

ปิด/เปิด PowerShell ใหม่ แล้วสำรองสักครั้งเพื่อดูว่าไฟล์ไปโผล่ที่ปลายทางจริง:

```powershell
node scripts\backup.mjs
```

- งานสำรองอัตโนมัติทุกวัน 02:00 ใช้ปลายทางเดียวกันเอง (Task Scheduler รับตัวแปรของผู้ใช้ไปด้วย)
- ตอนกู้คืนชี้ไปโฟลเดอร์นั้นได้ตรง ๆ: `node scripts\restore.mjs "<ปลายทาง>\2026-08-140659"`
- ไม่ตั้ง `BACKUP_DIR` = เก็บที่ `backups/` เหมือนเดิม (ใช้ได้ แต่ยังเสี่ยงเครื่องพังพร้อมกัน)

⚠️ **ไฟล์สำรองมีข้อมูลลูกค้าจริงและรหัสลับตัวแทน**
ปลายทางต้องเป็นที่ที่คนนอกเข้าไม่ถึง — ห้ามใช้โฟลเดอร์ที่แชร์ให้คนอื่น
และห้ามชี้กลับเข้ามาในโปรเจกต์นี้ (จะหลุดขึ้น git)

## ยังไม่ได้ทำ — ต้องตัดสินใจก่อน
- **เปิดบริการสำรองของผู้ให้บริการ** (ย้อนเวลากลับได้ทุกจุด) — ต้องอัปเกรดแผนใช้งาน มีค่าใช้จ่าย
  ถ้าเปิด จะได้ความสามารถที่วิธีของเราทำไม่ได้: กู้รหัสผ่านผู้ใช้ และย้อนกลับไปจุดเวลาใดก็ได้
