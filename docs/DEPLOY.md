# นำ Benjamin PMS ขึ้นเซิร์ฟเวอร์จริง

> **ใครทำ:** ผู้ที่มีสิทธิ์เข้า Supabase Dashboard + สิทธิ์ตั้งค่าเซิร์ฟเวอร์ที่จะใช้รัน
> **สถานะเอกสาร:** ปรับปรุง 7 ส.ค. 69 · แทนที่ `supabase/OPERATOR-SETUP.md` ในส่วนที่ล้าสมัย
> (ใบนั้นเขียนตอนมี migration 56 ไฟล์ ตอนนี้มี 130+ และมีขั้นตอนใหม่ที่ใบนั้นไม่มี)

## สิ่งที่ต้องรู้ก่อน

ระบบนี้เป็น **2 เว็บแยกกัน** ต้องมี 2 ที่อยู่:

| แอป | ใครใช้ | ตัวอย่างที่อยู่ |
|---|---|---|
| `apps/hq` | สำนักงานใหญ่ | `hq.benjamin-pms.com` |
| `apps/dealer` | ตัวแทนจำหน่าย | `dealer.benjamin-pms.com` |

ทั้งสองใช้ **ฐานข้อมูล Supabase ตัวเดียวกัน** (แยกสิทธิ์ด้วยกฎที่ฐานข้อมูล ไม่ได้แยกด้วยแอป)

## ขั้นที่ 1 — เตรียมฐานข้อมูล

ทำครั้งเดียว ถ้าเคยทำแล้วข้ามได้

```bash
npx supabase link --project-ref <รหัสโปรเจกต์>
npx supabase db push
```

**เช็กว่าผ่าน:** `npm run preflight` ต้องไม่ฟ้องเรื่อง "ฟังก์ชัน ... ยังไม่ได้ติดตั้ง"

### ⚠️ ต้องเปิดด้วยมือที่หน้าเว็บ Supabase (ลืมแล้วระบบพังทั้งระบบ)

1. **Authentication → Hooks → Customize Access Token** = `public.custom_access_token_hook`
   ถ้าไม่เปิด: ผู้ใช้ล็อกอินได้แต่ **เห็นข้อมูลว่างเปล่าทุกหน้า** เพราะไม่มีข้อมูลบทบาทติดมากับสิทธิ์
2. **Authentication → Sessions → Access token expiry** = `600` (10 นาที)
   ถ้าไม่ตั้ง: ปิดบัญชีพนักงานแล้วเขายัง**อ่านข้อมูลได้ต่ออีก 1 ชั่วโมง**

## ขั้นที่ 2 — ตั้งค่าลับบนเซิร์ฟเวอร์

**ห้ามใส่ค่าเหล่านี้ลงในโค้ดหรือ commit ขึ้น git เด็ดขาด** — ตั้งที่หน้าตั้งค่าของเซิร์ฟเวอร์เท่านั้น

### แอปสำนักงานใหญ่ (`apps/hq`)

| ตัวแปร | ค่า | ถ้าขาดแล้วเป็นอย่างไร |
|---|---|---|
| `NEXT_PUBLIC_DATA_SOURCE` | `supabase` | แอปไปอ่านข้อมูลตัวอย่างในเครื่องแทนข้อมูลจริง |

> โหมด `api` (คำขอเดินผ่าน backend ของเราเอง · ใบผ่านอยู่ใน cookie ที่หน้าเว็บอ่านไม่ได้) พร้อมแล้ว
> แต่**ยังไม่ได้เปิดใช้** — ขั้นตอนสลับ + วิธีถอยกลับอยู่ที่ [BACKEND-MIGRATION.md](BACKEND-MIGRATION.md#-ขั้นตอนสลับของจริงไปโหมด-api)
> ⚠️ ค่านี้ถูกฝังตอน build — แก้บน Vercel แล้วต้อง **Redeploy** ไม่งั้นไม่มีผล
| `NEXT_PUBLIC_SUPABASE_URL` | จาก Supabase → Settings → API | ต่อฐานข้อมูลไม่ได้เลย |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | จากที่เดียวกัน | ต่อฐานข้อมูลไม่ได้เลย |
| `SUPABASE_SERVICE_ROLE_KEY` | 🔒 **ลับสุด** จากที่เดียวกัน | จัดการตัวแทน/ผู้ใช้ไม่ได้ (ตอบ 501) |
| `DEALER_SECRET_KEY` | 🔒 สุ่มขึ้นมาเอง 32 ตัวอักษรขึ้นไป | ดูรหัสผ่านตัวแทนที่เก็บไว้ไม่ได้ |
| `NEXT_PUBLIC_DEALER_APP_URL` | ที่อยู่จริงของแอปตัวแทน | ปุ่ม "เข้าระบบแทนตัวแทน" พาไปผิดที่ |

### แอปตัวแทน (`apps/dealer`)

`NEXT_PUBLIC_DATA_SOURCE` · `NEXT_PUBLIC_SUPABASE_URL` · `NEXT_PUBLIC_SUPABASE_ANON_KEY`

> 🔒 **แอปตัวแทนต้องไม่มี `SUPABASE_SERVICE_ROLE_KEY`** — ไม่ได้ใช้ และการมีไว้เฉย ๆ คือความเสี่ยงเปล่า ๆ

## ขั้นที่ 3 — ตรวจความพร้อมก่อนกดขึ้นระบบ

```bash
npm run preflight
```

ตรวจให้ 10 ข้อในคำสั่งเดียว: ตัวแปรครบไหม · โหมดข้อมูลถูกไหม · ต่อฐานข้อมูลได้ไหม ·
migration ครบไหม · ข้อมูลรั่วถึงคนที่ไม่ได้ล็อกอินไหม · มีผู้ดูแลสูงสุดไหม ·
ทุกสาขามีบัญชีไหม · มีข้อมูลทดสอบปนไหม · อายุใบผ่านสั้นพอไหม

**ต้องขึ้น ✅ ทุกข้อก่อนไปต่อ** — ทุกข้อที่ตรวจคือสิ่งที่ถ้าพลาดแล้วผู้ใช้ใช้งานไม่ได้จริง

พร้อมกับตรวจคุณภาพโค้ดชุดเต็ม:

```bash
npm run typecheck && npm run lint && npm run checks && npm run test:unit && npm run test
```

## ขั้นที่ 4 — สั่ง build และรัน

```bash
npm run build          # build ทั้งสองแอป
```

รันแต่ละแอปด้วย `next start` จากโฟลเดอร์ของตัวเอง (พอร์ตแยกกัน)

### ⚠️ ต้องรันในโหมด production เท่านั้น (`NODE_ENV=production`)

โหมดพัฒนากับโหมดจริง **ใช้กฎความปลอดภัยคนละชุด** — โหมดจริงเท่านั้นที่เปิดการกัน XSS
แบบเต็มรูปแบบ (รหัสยืนยันสุ่มใหม่ทุกคำขอ) ถ้าเผลอรันโหมดพัฒนาบนเซิร์ฟเวอร์จริง
จะได้ระบบที่ **ดูเหมือนทำงานปกติแต่ไม่มีเกราะกัน XSS เลย**

## ขั้นที่ 5 — ยืนยันหลังขึ้นระบบ

```bash
curl https://<ที่อยู่ HQ>/api/health
curl https://<ที่อยู่ตัวแทน>/api/health
```

ต้องได้ `"status":"ok"` และรหัส 200 · ถ้าได้ 503 ให้ดูในคำตอบว่าข้อไหนไม่ผ่าน

**ตั้งให้ตัวเฝ้าระวังยิงถามที่อยู่นี้ทุก 1–5 นาที** แล้วแจ้งเตือนเมื่อได้ 503 ติดกัน 2 ครั้ง
(ตัวเฝ้าระวังจะเป็นตัวบอกว่าระบบล่ม แทนที่จะรอผู้ใช้โทรมาแจ้ง)

### เช็กด้วยตาอีก 3 อย่าง

1. เปิดหน้าเข้าระบบทั้งสองแอป → ล็อกอินได้จริง
2. กดปุ่มสักปุ่ม (เช่น "เพิ่มลูกค้าเป้าหมาย") → หน้าต่างเปิดขึ้นมาได้
   ถ้าหน้าขึ้นแต่กดอะไรไม่ได้เลย = กฎความปลอดภัยบล็อกสคริปต์ ให้ตรวจว่ารันโหมด production จริงไหม
3. พิมพ์ใบเสนอราคาสักใบ → ตัวหนังสือต้องเป็นฟอนต์ Sarabun ไม่ใช่ฟอนต์สำรอง

## ถ้าต้องย้อนกลับ

- **โค้ด:** กลับไป deploy commit ก่อนหน้า
- **ฐานข้อมูล:** ⚠️ migration ย้อนกลับอัตโนมัติไม่ได้ ต้องเขียนใบใหม่แก้กลับ
  **ก่อนรัน `db push` ทุกครั้ง ให้สั่ง `npm run backup` ก่อนเสมอ**

  ⚠️ **อย่าพึ่งการสำรองอัตโนมัติของผู้ให้บริการ** — ตรวจแล้วพบว่าแผนใช้งานปัจจุบัน
  **ไม่มีข้อมูลสำรองอยู่เลยสักชุด** (`backups: []`, ย้อนเวลากลับ: ปิดอยู่)
  ข้อมูลหาย = หายถาวร · รายละเอียดและวิธีกู้อยู่ที่ [BACKUP.md](BACKUP.md)

## สิ่งที่ยังไม่ได้ทำ (ตั้งใจ — รอการตัดสินใจ)

- **ไฟล์ตั้งค่าเฉพาะผู้ให้บริการ** (Vercel / Docker) — ยังไม่รู้ว่าจะใช้แบบไหน
- **ระบบแจ้งเตือนเมื่อระบบล่ม** — **ตั้ง `NEXT_PUBLIC_SENTRY_DSN` อย่างเดียวจบ ไม่มีขั้นตอนที่สอง**
  ครอบคลุมทั้งข้อผิดพลาดฝั่งผู้ใช้และฝั่งเซิร์ฟเวอร์ (รวม API) · CSP เปิดทางให้เองตาม DSN
  ยังไม่ตั้ง = ระบบล่มแล้วจะรู้ตัวก็ต่อเมื่อผู้ใช้โทรมาแจ้ง (`npm run preflight` เตือนข้อนี้ให้)
- ~~แผนสำรองข้อมูล/ทดลองกู้คืน~~ — **ทำแล้ว** ดู [BACKUP.md](BACKUP.md)
  (สำรองอัตโนมัติตามเวลา และเก็บไฟล์ไว้นอกเครื่อง ยังต้องตัดสินใจ)

## เว็บจริงตอนนี้อัปขึ้นอย่างไร (ปรับปรุง 1 ก.ย. 69)

| ที่อยู่ | โปรเจกต์บน Vercel | โฟลเดอร์ที่ build |
|---|---|---|
| https://benjamin-hq.vercel.app | `benjamin-hq` | `apps/hq` |
| https://benjamin-dealer.vercel.app | `benjamin-dealer` | `apps/dealer` |

**ตั้งแต่ 1 ก.ย. 69 เชื่อม GitHub เข้ากับ Vercel แล้ว — push แล้วขึ้นเว็บจริงเอง**

```
เครื่องพัฒนา ──push──> GitHub (MazDev01/pms · branch monorepo) ──> Vercel ──> เว็บจริง (~1-2 นาที)
```

ก่อน build ทุกครั้ง Vercel จะเรียก **ด่านตรวจ** `scripts/vercel-should-build.mjs`
(ตั้งไว้ที่ `apps/*/vercel.json` → `ignoreCommand`) ซึ่งจะ **ไม่ขึ้นเว็บจริง** เมื่อ

| กรณี | ผล |
|---|---|
| ข้อความคอมมิตมี `[skip deploy]` · `[wip]` · `[ยังไม่เสร็จ]` | ข้าม — เก็บงานไว้บน GitHub ก่อน |
| คอมมิตแตะแต่ `docs/` `tests/` `.github/` `README` | ข้าม — เว็บไม่มีอะไรเปลี่ยน |
| รันในเครื่องแล้วชุดกันพลาด/typecheck ไม่ผ่าน | ข้าม |

⚠️ กติกาของ `ignoreCommand` กลับด้านกับปกติ: **จบด้วยรหัส 0 = ข้าม · 1 = build ต่อ**
ระวังตอนแก้ไฟล์นี้ — สคริปต์ที่พังจะจบด้วยรหัส 1 ซึ่งแปลว่า "ให้ build" (ด่านจะดูเหมือนทำงานทั้งที่พัง)
วิธีตรวจว่าใช้ได้จริง: ดูล็อกของ Vercel ต้องเห็นบรรทัด `✅ ขึ้นเว็บจริงได้` หรือ `⛔ ไม่ขึ้นเว็บจริง`

**คุณภาพโค้ดตรวจที่ GitHub Actions** (`.github/workflows/ci.yml`): typecheck + เทสต์ย่อย + ชุดกันพลาด ทุก push

**อัปด้วยมือ (เมื่อจำเป็น เช่น เปลี่ยนค่า env แล้วอยาก build ใหม่ทันที):**

คำสั่งอัปขึ้นเว็บจริง (ทำทีละแอป · สั่งจาก **รากโปรเจกต์** เท่านั้น ไม่ใช่ในโฟลเดอร์แอป):

```bash
npx vercel link --project benjamin-hq --yes && rm -f .env.local
npx vercel deploy --prod --yes

npx vercel link --project benjamin-dealer --yes && rm -f .env.local
npx vercel deploy --prod --yes
```

⚠️ `vercel link` จะสร้าง `.env.local` ที่รากโปรเจกต์ทิ้งไว้ — ลบทุกครั้ง ไม่งั้นค่าที่ดึงมาจะไปทับ
ค่าของแอปตอนรันในเครื่อง

**ค่าที่ต้องมีบนเว็บจริง** (ตั้งที่ Vercel → Project → Settings → Environment Variables):

| แอป | ตัวแปร | ค่า | ไม่ตั้งแล้วเกิดอะไร |
|---|---|---|---|
| ตัวแทน | `NEXT_PUBLIC_HQ_ORIGIN` | ที่อยู่แอปสำนักงานใหญ่ | หน้าบัญชีขึ้น "ยังไม่ได้ตั้งค่า…" เปลี่ยนอีเมล/รหัสผ่านไม่ได้ |
| สำนักงานใหญ่ | `DEALER_APP_ORIGIN` | ที่อยู่แอปตัวแทน | คำขอจากแอปตัวแทนถูกปฏิเสธข้ามต้นทาง (CORS) |

**ถ้าอยากให้ push แล้วขึ้นเว็บเอง** ต้องเชื่อมโปรเจกต์กับ GitHub ก่อน (ทำทีละโปรเจกต์):

```bash
npx vercel link --project benjamin-hq --yes
npx vercel git connect https://github.com/MazDev01/pms
```

เชื่อมแล้วต้องตั้ง **Production Branch = `monorepo`** ที่ Settings → Git ด้วย
(ค่าเริ่มต้นคือ `main` ซึ่งเราไม่ได้ใช้ — ถ้าไม่ตั้ง จะได้แค่ Preview ไม่ขึ้นเว็บจริง)
