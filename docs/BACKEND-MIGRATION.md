## ทำไมต้องทำ

ตอนนี้หน้าเว็บยิงเข้าฐานข้อมูลตรง ๆ ด้วยกุญแจ `anon` แล้วให้ฐานข้อมูลตรวจสิทธิ์เอง (RLS)
ใช้งานได้ดีและเร็ว แต่มีช่องโหว่ที่ปิดด้วย RLS ไม่ได้:

**กฎธุรกิจที่อยู่ในหน้าเว็บ ข้ามได้** — RLS ตอบได้แค่ *"แถวนี้เป็นของสาขาคุณไหม"*
ตอบไม่ได้ว่า *"ตอนนี้ทำแบบนี้ถูกกติกาธุรกิจไหม"*

ตัวอย่างจริง: กฎ "ลบลูกค้าไม่ได้ถ้ายังมีดีลที่ขายอยู่" อยู่ใน `customerDeletion.ts` ฝั่งหน้าเว็บ
คนที่ล็อกอินแล้วเปิด Console สั่งลบตรงเข้าฐานข้อมูลได้เลย RLS ไม่ห้าม เพราะลูกค้ารายนั้น
เป็นของสาขาเขาจริง ๆ

## โครงที่ทำให้ทำได้แบบไม่ต้องรื้อ

ระบบมีชั้นข้อมูลแยกไว้อยู่แล้วตั้งแต่ต้น — **ไม่มีหน้าไหน import supabase-js เลย**

```
หน้าเว็บทุกหน้า ──► DataAdapter (18 กลุ่มงาน) ──┬─► LocalAdapter    ข้อมูลตัวอย่างในเครื่อง
                     packages/shared/lib/data/  ├─► SupabaseAdapter ยิงเข้า DB ตรง (ใช้อยู่ตอนนี้)
                                                └─► HttpAdapter     คุยผ่าน backend  ◄── ของใหม่
```

สลับด้วย `NEXT_PUBLIC_DATA_SOURCE` ตัวเดียว → **ย้ายได้โดยไม่แตะโค้ดหน้าเว็บสักบรรทัด**
และถ้าไปต่อไม่ไหว สลับกลับได้ทันที

- **ค่ากลาง** (นโยบาย/เกณฑ์วันเตือน/วันนี้ของระบบ) ยังเติมที่ฝั่งแอป เซิร์ฟเวอร์คืน "ดิบ"

## ⚠️ กับดักที่เจอจริงในระยะนี้ — ทั้งคู่ "ไม่มีอะไรฟ้อง"

### 1. ถาม "มี backend จริงไหม" ด้วยคำถามผิด

โค้ด **29 จุด** เช็ค `DATA_SOURCE === "supabase"` เพื่อจะถามว่า *"มีบัญชี/สิทธิ์/ข้อมูลจริงไหม"*
ซึ่งถูกตอนมีแค่ 2 โหมด แต่พอเพิ่มโหมด `api` คำถามสองข้อนี้แยกจากกันแล้ว

- รอบแรก (11 จุด): **ล็อกอินไม่ได้เลยทั้งระบบ** — ทุกด่านตกไปใช้ทางเดโม
- รอบสอง (18 จุด ใน `useNetworkData.ts` และเพื่อน ๆ): หน้า HQ เจาะสาขาโชว์ลูกค้าเป้าหมาย
  **0 แถว ทั้งที่ในฐานมี 9 ราย** — หน้าจอไม่พัง ไม่มี error ในคอนโซล แค่ว่างเปล่าเฉย ๆ
  (`APP_NOW` ก็โดนด้วย → ใบที่สร้างใหม่ลงวันที่ผิดปี)

แยกเป็น `REAL_BACKEND` (= supabase หรือ api) ออกจาก `DATA_SOURCE` (= ใช้อะแดปเตอร์ตัวไหน) แล้ว
และเพิ่มตัวตรวจ [`check-real-backend.mjs`](../scripts/check-real-backend.mjs) เข้า `npm run checks`
เพื่อไม่ให้กลับมาอีก

### 2. ชุดทดสอบเองก็ผูกกับ URL ของ Supabase

- `SUPABASE_MODE` ในชุดทดสอบเช็คแบบเดียวกัน → **ทั้งชุดข้ามตัวเองเงียบ ๆ** แล้วรายงานว่า "ผ่าน"
  ทั้งที่ไม่ได้ทดสอบอะไรเลย (เปลี่ยนเป็น `REAL_BACKEND` แล้ว)
- เทสต์ที่จำลองความล้มเหลวดักที่ `/rest/v1/<ตาราง>` ตรง ๆ — โหมด `api` ยิงไปที่ `/api/v1/...`
  คำสั่งจึงไม่เคยถูกตัด เทสต์ล้มเหมือนระบบมีบั๊ก ทั้งที่เทสต์ดักผิดที่
  (แก้ให้ดักทั้งสองโหมดแล้ว: `silent-read-failure` · `edge-cases-sales` · `func-appt-files` · `stale-list-overwrite`)

### ระยะ 2 · ย้ายกฎธุรกิจลงฐานข้อมูล — เสร็จแล้ว ✅

**ทำไมลงฐานข้อมูล ไม่ใช่ขึ้น backend:** โหมดที่ใช้งานจริงคือ `supabase` (หน้าเว็บยิงเข้าฐานตรง)
กฎที่วางไว้ใน `/api/v1` จะยังไม่มีผลจนกว่าจะถึงระยะ 4 · วางที่ฐานข้อมูล = **มีผลทันทีวันนี้**
และเป็นวิธีที่ระบบใช้อยู่แล้วหลายจุด (`delete_dealer_atomic` · `close_won_quotation` ฯลฯ)

**เสร็จแล้ว — [`0141`](../supabase/migrations/0141_customer_delete_cascade.sql):**

| กฎ | เดิม | ตอนนี้ |
|---|---|---|
| ยังมีดีลที่ขายอยู่ = ลบลูกค้าไม่ได้ | อยู่ในหน้าเว็บอย่างเดียว | RPC `delete_customer_cascade` ปฏิเสธที่ฐานข้อมูล |
| ดีลที่จบแล้ว = ประวัติลูกค้า ลบไปพร้อมกัน | 4+ คำสั่งแยกกัน เน็ตหลุด = หายครึ่งเดียว | ทรานแซกชันเดียว ได้ทั้งก้อนหรือไม่ได้เลย |
| ลบดีลที่ยังมีใบผูกอยู่ | FK เป็น `set null` → ลบผ่าน แล้วใบถูกตัดสายเงียบ ๆ | `restrict` → ปฏิเสธ ตรงกับที่หน้าเว็บบอกผู้ใช้ |

พิสูจน์ด้วย [`business-rules-at-db.spec.ts`](../tests/scenario/business-rules-at-db.spec.ts) —
เล่นบท "คนที่ล็อกอินได้แล้วสั่งงานเข้าฐานข้อมูลตรง ๆ" ข้ามหน้าเว็บทั้งหมด ผ่าน 4/4

> กดผ่านหน้าจอพิสูจน์ได้แค่ "ปุ่มไม่โผล่" ซึ่งข้ามได้ — ต้องยิงตรงเท่านั้นถึงจะรู้ว่าฐานข้อมูลกันจริง

**ที่ยังคงไว้ฝั่งหน้าเว็บโดยตั้งใจ:** `customerDeletionImpact` ยังคำนวณอยู่ — แต่ทำหน้าที่
"บอกผู้ใช้ล่วงหน้าว่าจะเกิดอะไร" (กล่องยืนยัน) เท่านั้น **คนตัดสินคือฐานข้อมูล**
ข้อมูลเปลี่ยนระหว่างนั้นก็ถูกปฏิเสธเอง

**เสร็จแล้ว — [`0142`](../supabase/migrations/0142_quotation_total_matches_boq.sql) (`boq.ts`):**

ยอดในใบเสนอราคาต้องเท่ากับ Σ(จำนวน × ราคา/หน่วย) ของรายการ BOQ ในใบนั้น

ยอดนี้ไหลต่อไปเป็นยอดขายของสาขาและยอดสะสมของลูกค้า ส่วนรายการ BOQ คือสิ่งที่ลูกค้าเห็น
บนเอกสารที่พิมพ์ออกไป — ไม่ตรงกัน = เอกสารบอกราคาหนึ่ง ระบบรายงานอีกราคาหนึ่ง

ตรวจแล้วว่าหน้าเว็บคิดยอดจาก BOQ ให้เสมอ **ไม่มีช่องให้พิมพ์ยอดเองสักที่เดียว** ทั้งสองฟอร์ม
จึงบังคับที่ฐานข้อมูลได้โดยไม่กระทบการใช้งานจริง (ฐานจริง+ฐานทดสอบไม่มีใบที่ยอดไม่ตรงเลยสักใบ)

**ตอนนี้เส้นทางเงินถูกการันตีที่ฐานข้อมูลครบสาย:**

```
รายการ BOQ ──0142──► ยอดในใบ ──0114──► ยอดสะสมของลูกค้า
```

### `closeWon.ts` — ตรวจแล้ว ตั้งใจไม่บังคับที่ฐานข้อมูล

กติกาคือ "ปิดการขายสำเร็จแล้วต้องเดินงานตามหลังให้ครบ" (สร้าง/ผูกลูกค้า + ปิดใบ + รวมยอด)
งานตามหลังเป็น RPC เดียว atomic อยู่แล้ว (`close_won_quotation`)

อยากบังคับเป็นกฎ *"ดีลที่ปิดการขายสำเร็จ ต้องผูกลูกค้าเสมอ"* — แต่**ทำไม่ได้**:
หน้าเว็บเขียนสถานะ `PAID` ลงก่อน แล้วค่อยสร้าง/ผูกลูกค้าเป็นจังหวะถัดไป
ใส่กฎนี้ = ปฏิเสธเส้นทางปกติของระบบเอง · จะบังคับได้ต้องสลับลำดับการเขียน ซึ่งคือการ
เปลี่ยนตรรกะธุรกิจ ไม่ใช่การย้ายที่อยู่ของกฎ — เกินขอบเขตระยะนี้

**สิ่งที่คุ้มครองอยู่แล้ว:** ตัวเลขเงินไม่พึ่งเส้นทางนี้ — `0114` คำนวณยอดลูกค้าใหม่เองทุกครั้ง
ที่ใบเปลี่ยน ต่อให้แอปลืมสั่ง (หรือสั่งไม่สำเร็จ) ยอดก็ยังตรง

**เหลือทำ:** ตรรกะที่เหลือใน `SalesContext` (ส่วนใหญ่เป็นการประสานงานหน้าจอ ไม่ใช่กฎที่ข้ามแล้วเสียหาย)

### บั๊ก 3 ตัวที่เจอตอนรันชุดเต็ม — ทีละตัวไม่เจอเลย

รอบแรกรายงานว่า "ผ่าน" ทั้งที่ทดสอบแค่ทีละสเปก · พอรันชุดเต็มจริง **ล้ม 153 ข้อ**
บทเรียน: งานที่แตะการเชื่อมต่อระดับนี้ **ห้ามสรุปก่อนรันชุดเต็ม**

| # | ต้นเหตุ | อาการที่เห็น |
|---|---|---|
| 1 | `setAuth()` เป็น async แต่เรียกลอย ๆ ไม่ await/ไม่ catch | ใบผ่านหมดอายุ → unhandled rejection → **Node ปิดโปรเซสทั้งตัว** |
| 2 | สายปิดเร็วแล้วต่อใหม่ทันทีแบบไม่หน่วง | วนไม่หยุด **ถล่มเซิร์ฟเวอร์ตัวเอง** จนทุกหน้าเปิดไม่ขึ้น |
| 3 | `runtime`/`dynamic` ที่ re-export มา Next.js อ่านไม่เห็น | เตือน 84 ครั้ง "ใช้ค่าเริ่มต้นแทน" — ค่าที่ตั้งไม่เคยมีผลเลยทั้ง 19 เส้นทาง (ค้างมาตั้งแต่ระยะ 1) |

เกณฑ์ข้อ 2 ที่ใช้ตอนนี้: สายอยู่ได้เกิน 5 วินาที = ปกติ (ต่อใหม่ได้ไว) · ปิดเร็วกว่านั้น = ถอยห่างขึ้นเรื่อย ๆ
และไม่ว่ากรณีไหน **ห้ามยิงติดกันโดยไม่เว้นวรรค**

#### สามเรื่องที่ต้องระวังในโค้ดนี้

1. **`realtime.setAuth(token)` ห้ามลืม** — realtime มีชั้นยืนยันตัวตนแยกจาก `global.headers`
   ลืมแล้วช่องจะต่อแบบไม่มีตัวตน · ผลที่แย่กว่าคือ "ได้รับของทุกสาขา" ซึ่งหน้าจอดูปกติทุกอย่าง
   → มีเทสต์ที่ *รอแล้วยืนยันว่าไม่มีอะไรมา* คู่กับเทสต์ว่าของมาถึง
   ([`realtime-sse.spec.ts`](../tests/scenario/realtime-sse.spec.ts) ผ่าน 3/3)
2. **ไม่ใช้ `EventSource`** ทั้งที่มีมาให้ในเบราว์เซอร์ — มันแนบ header ไม่ได้ ต้องส่งใบผ่านไปทาง URL
   ซึ่งจะไปโผล่ใน log ของทุกตัวกลาง · ใช้ `fetch` + อ่านสายเองแทน
3. **สายถูกปิดเป็นระยะโดยตั้งใจ** — เซิร์ฟเวอร์ไร้เซิร์ฟเวอร์มีเพดานอายุคำขอ (Vercel Hobby = 60 วินาที)
   เซิร์ฟเวอร์จึงปิดเองอย่างสุภาพที่ 50 วินาที (`REALTIME_SSE_MAX_SECONDS`) แล้วฝั่งเบราว์เซอร์ต่อใหม่ทันที
   **ผลข้างเคียงที่ต้องรู้:** ต่อใหม่ทุก ~50 วินาทีต่อแท็บที่เปิดอยู่ — ถ้าย้ายไปแพ็กเกจที่ให้ยาวกว่านี้
   ปรับ ENV ตัวนี้ให้สูงขึ้นได้เลย
4. **รอบที่ค้างอยู่ต้องรู้ว่าตัวเองเป็นรอบเก่า** — React โหมดพัฒนาเรียก effect ซ้ำ (mount → unmount → mount)
   ตัวเลิกรับตัวสุดท้ายสั่งหยุด แล้วตัวสมัครตัวใหม่สั่งเริ่มในจังหวะเดียวกัน
   ถ้าเช็กแค่ธง "กำลังทำงานอยู่ไหม" รอบเก่าที่ค้างที่ `await` จะวนต่อ = เปิดสายซ้อนสองสาย
   **อาการที่เห็นคือ event มาซ้ำสองครั้ง ซึ่งไล่หายากมาก** → ใช้เลขรอบ (`gen`) กำกับทุกจุดที่ await เสร็จ
5. **เก็บช่องคืนให้ครบทุกทางออก** — `removeChannel` คืน promise ปล่อย reject ลอยได้
   และบางครั้งเบราว์เซอร์หายไปดื้อ ๆ โดย `cancel()` ไม่ถูกเรียก จึงผูก `req.signal` ไว้อีกทาง
   ไม่งั้นช่อง realtime ค้างกินโควตาฝั่ง Supabase สะสมไปเรื่อย ๆ

### ระยะ 4 · ปิดประตูฐานข้อมูล — โค้ดเสร็จแล้ว (ยังไม่เปิดใช้จริง)

[`server/v1/auth.ts`](../packages/shared/server/v1/auth.ts) · [`server/v1/_cookie.ts`](../packages/shared/server/v1/_cookie.ts) · [`lib/cookieAuth.ts`](../packages/shared/lib/cookieAuth.ts)

#### ⚠️ แผนเดิมเขียนไว้ผิด — "ถอนสิทธิ์ anon" ทำแล้วไม่ได้อะไร

ตรวจก่อนลงมือแล้วพบว่า:

1. **กุญแจสาธารณะถูกปิดไปหมดแล้ว** — [`anon-exposure.spec.ts`](../tests/scenario/anon-exposure.spec.ts)
   ยืนยันว่าคนที่ยังไม่ล็อกอินอ่าน/เขียนไม่ได้เลยทั้ง 23 ตาราง/วิว → ถอนอีกก็ไม่เปลี่ยนอะไร
2. **ประตูที่เปิดจริงคือใบผ่านของคนที่ล็อกอินแล้ว** ซึ่งวางอยู่ใน localStorage ให้ JavaScript หยิบได้
   และ backend ของเราก็ใช้ใบเดียวกันนั้น (นโยบายระยะ 1) — ถอนสิทธิ์ตัวนี้ backend จะพังไปด้วย

ถ้าทำตามแผนตรงตัว จะได้ "ความรู้สึกว่าปิดแล้ว" ทั้งที่ประตูยังเปิดอยู่ ซึ่งอันตรายกว่าไม่ทำ

#### ทางที่เลือก: ย้ายใบผ่านไปไว้ใน cookie ที่ JavaScript อ่านไม่ได้

```
เดิม   เบราว์เซอร์ ── ใบผ่านใน localStorage ──► ฐานข้อมูล      (JavaScript หยิบไปใช้เองได้)
ตอนนี้ เบราว์เซอร์ ── cookie httpOnly ──► backend ──► ฐานข้อมูล  (หยิบไม่ได้)
```

- `POST /api/v1/auth?op=login` — เซิร์ฟเวอร์คุยกับ Supabase แทน แล้วตั้ง cookie ให้
  **ห้ามส่ง access_token/refresh_token กลับไปใน body** จะเสียจุดประสงค์ทั้งหมด
- `GET /api/v1/auth` — บอกแค่ "เป็นใคร" (บทบาท/สาขา/ชื่อ) ไม่มีใบผ่านปนมา
- `?op=refresh` — ต่ออายุที่เซิร์ฟเวอร์ · `apiFetch` เจอ 401 แล้วต่ออายุให้เองแล้วลองใหม่ 1 ครั้ง
- `?op=logout` — ปิด session ฝั่ง Supabase ด้วย ไม่ใช่แค่ลบ cookie

**RLS 72 กฎยังเป็นตัวกันหลักเหมือนเดิม** — เลือกทางนี้แทนการให้ backend ถือ `service_role`
เพราะทางนั้น RLS จะเลิกคุ้มครองการใช้งานปกติ แล้วต้องเขียนการกันข้ามสาขาเองทั้ง 19 เส้นทาง
พลาดจุดเดียว = ข้อมูลสาขาอื่นรั่วโดยไม่มีอะไรจับได้

#### จุดที่ต้องระวัง

- **โหมด supabase ต้องไม่เปลี่ยนพฤติกรรมเลย** — หน้าเว็บยังต้องถือใบผ่านเองเพื่อคุยฐานข้อมูลตรง
  ทุกจุดจึงคุมด้วย `DATA_SOURCE === "api"` ไม่ใช่ `REAL_BACKEND`
- **เซิร์ฟเวอร์ยังรับ `Authorization` ไว้ด้วย** — สคริปต์ดูแลระบบและชุดทดสอบยิงด้วย Bearer
  ตัดทิ้งทันทีจะพังเป็นแถบ · ตัดได้เมื่อย้ายครบทุกจุดแล้ว
- **โหมด api หน้าเว็บอ่านชื่อคน/ชื่อสาขาเองไม่ได้แล้ว** — ถ้าไม่ให้เซิร์ฟเวอร์ส่งมาให้
  หน้าจอจะโชว์อีเมลแทนชื่อคน และรหัสสาขาแทนชื่อบริษัท แบบเงียบ ๆ

พิสูจน์ด้วย [`auth-cookie.spec.ts`](../tests/scenario/auth-cookie.spec.ts) — ข้อสำคัญที่สุดคือ
**"cookie เป็น httpOnly จริงไหม"** ถ้าตั้งพลาด ทุกอย่างทำงานเหมือนเดิมเป๊ะ ต่างแค่ประตูยังเปิด

"แกว่ง" = ล้มรอบแรกแล้วผ่านตอนลองใหม่ · ทุกตัวเป็น timeout ตอนเปิดหน้า ไม่ใช่ปัญหาสิทธิ์
จำนวน "ข้าม" ต่างกันเพราะเทสต์บางชุดออกแบบมาให้รันเฉพาะโหมดเดียว

#### เหลือทำก่อนปิดประตูได้จริง

ทั้งหมดนี้จะมีผลก็ต่อเมื่อ **สลับของจริงเป็นโหมด api** — ตอนนี้ยังเป็นโหมด supabase
ตราบใดที่ยังไม่สลับ หน้าเว็บก็ยังถือใบผ่านเองอยู่ดี (ตามที่โหมดนั้นต้องการ)

#### บั๊ก 5 ตัวที่โผล่ตอนรันชุดเต็ม — 2 ตัวมีอยู่ในโหมดปัจจุบันด้วย

การย้ายมาโหมด api ทำให้ "ความล้มเหลวเงียบ" กลายเป็น 401 ที่เห็นได้ นี่คือของที่โผล่ออกมา

**1. ต่ออายุใบผ่านพร้อมกันหลายสาย → ผู้ใช้เด้งออกทั้งที่เพิ่งล็อกอิน**
เปิดหน้าเดียวยิงคำขอพร้อมกันสิบกว่าสาย ใบผ่านหมดอายุพอดี = ทุกสาย 401 พร้อมกัน
แล้วขอต่ออายุพร้อมกันสิบกว่าครั้ง · refresh token ของ Supabase ใช้ได้ครั้งเดียวแล้วเปลี่ยนใบใหม่
สายแรกสำเร็จและเผาใบเก่าทิ้ง ที่เหลือใช้ใบที่ถูกเผาแล้ว → ล้มหมด
แก้: `caRefresh()` เป็นสายเดียวร่วมกัน ([`cookieAuth.ts`](../packages/shared/lib/cookieAuth.ts))

**2. ลบ/ปิดสาขาแล้ว หน้าที่เปิดค้างยังใช้ต่อได้** ⚠️ ความปลอดภัย
บั๊กเดียวกับที่ผู้ใช้แจ้ง 14 ส.ค. 69 และแก้ไปแล้วที่ `supabaseAuth.stillValid` —
แต่ตอนย้ายมาโหมด api ด่านนั้นไม่ได้ตามมา (คนละเส้นทางการฟื้น session)
แก้: ใส่ด่านเดียวกันเป๊ะที่ [`server/v1/auth.ts`](../packages/shared/server/v1/auth.ts) ทั้ง login/refresh/who-am-I
พร้อมล้าง cookie ทิ้งเมื่อเจอ ⚠️ **บทเรียน: ย้ายเส้นทาง auth = ต้องไล่ด่านเก่าทุกด่านว่าตามมาครบไหม**

**3. ปุ่ม "เข้าระบบแทนตัวแทน" ใช้ไม่ได้เลย**
ลิงก์เข้าระบบครั้งเดียว (magic link) ส่งใบผ่านกลับมาทาง `#hash` ของ URL เสมอ
โหมด supabase มี supabase-js คอยรับ · โหมด api ไม่มีใครรับ → HQ กดแล้วเจอหน้าเข้าสู่ระบบเปล่า
แก้: เพิ่ม `op=adopt` ที่เซิร์ฟเวอร์ (ยืนยันใบผ่านกับ Supabase ก่อนเสมอ ห้ามเชื่อสิ่งที่เบราว์เซอร์ส่งมา)
+ `caAdoptFromUrl()` ที่หน้าเว็บ อ่าน hash → แลกเป็น cookie → ลบออกจาก URL ทันที

**4. หน้าเข้าสู่ระบบยิงคำขอในนามสาขาเดโม (CNX)** — *มีอยู่ในโหมดปัจจุบันด้วย*
`hydrated` แปลว่า "ฟื้น session เสร็จแล้ว" ซึ่งเป็นจริงแม้ผลคือ "ไม่มี session"
ค่าเริ่มต้นของ session คือสาขาเดโม CNX → ยังไม่มีใครล็อกอินแต่ยิง `leads/customers/quotations?dealer=CNX` ออกไปจริง
โหมด supabase มองไม่เห็นเพราะ RLS ปฏิเสธเงียบ ๆ
แก้: `ready = hydrated && (ไม่ใช่ backend จริง || ล็อกอินแล้ว)` ใน [`SalesContext.tsx`](../packages/shared/context/SalesContext.tsx)

**5. ค่า VAT / อายุใบเสนอราคา ถูกอ่านก่อนล็อกอิน → ตกไปใช้ค่าตั้งต้น** — *มีอยู่ในโหมดปัจจุบันด้วย* ⚠️ คิดเงินผิดได้
[`useHQConfig.ts`](../packages/shared/lib/useHQConfig.ts) ยิงอ่านตั้งแต่ mount ไม่รอรู้ตัวตน
โหมด supabase ถูกปฏิเสธเงียบ ๆ แล้ว fallback เป็น `DEFAULT_HQ_POLICY` — **ซึ่งอันตรายกว่า 401 เสียอีก**
เพราะใบเสนอราคาจะถูกออกด้วย VAT/วันหมดอายุที่ไม่ใช่ค่าที่ HQ ตั้งไว้ โดยไม่มีอะไรฟ้อง
แก้: gate เดียวกับข้อ 4

#### บั๊กอีก 2 ตัวที่โผล่หลังสลับของจริง (18 ส.ค. 69)

**6. บัญชีผิดฝั่งเข้าได้ แล้วไปเจอหน้า 404** (ผู้ใช้แจ้งเอง)
เอารหัสสำนักงานใหญ่กรอกที่หน้าเข้าสู่ระบบของ *ตัวแทน* แล้วเข้าได้จริง แถมถูกพาไป
`/hq/dashboard` ซึ่งไม่มีอยู่ในแอปตัวแทน
ต้นเหตุ: `LoginCard` ดูแค่ "บัญชีนี้เป็น HQ หรือตัวแทน" แล้วส่งไปตามนั้น
**ไม่เคยถามว่าแอปที่เขายืนอยู่ใช่ที่ของเขาหรือเปล่า** — มีมาตั้งแต่โหมดเดิม เพิ่งเห็นเพราะไปโผล่ 404
แก้: ปฏิเสธพร้อมบอกทางที่ถูก **และสั่งออกจากระบบด้วย** — จังหวะที่ตรวจเจอนั้นใบผ่านถูกออกไปแล้ว
ถ้าลืมล้าง = มีใบผ่านของคนสำนักงานใหญ่ค้างอยู่บนโดเมนของตัวแทน (ตรงข้ามกับเป้าหมายของระยะ 4)
ล็อกไว้ด้วย [`wrong-app-login.spec.ts`](../tests/scenario/wrong-app-login.spec.ts) ตรวจสองทาง + ตรวจว่าไม่มีใบผ่านค้าง

`/dealers` `/profile` `/metrics` `/settings?k=leadRules|notifRules` `/dealer-settings?dealer=CNX`
⚠️ **บทเรียน: ไล่ปะทีละจุดพลาดสองรอบติด** — เปลี่ยนมาทำด่านกลางตัวเดียว
[`useAuthReady.ts`](../packages/shared/lib/useAuthReady.ts) แล้ววางที่ `useRepoState`
(ทางผ่านของ 15 ไฟล์) + hook ที่ยิง repo เองอีก 22 จุด
⚠️ **กับดักซ้อน: ใส่ด่านแล้วต้องเติม `ready` ลง dependency ของ effect ด้วย**
ไม่งั้นพอล็อกอินเสร็จ effect ไม่ทำงานใหม่ → เข้าระบบได้แต่ข้อมูลไม่ขึ้นเลย (เกือบปล่อยผ่าน)

#### เสียงที่ "ต้องมี" ไม่ใช่บั๊ก

401 ตอนถามว่า "ตอนนี้เป็นใคร" ในสถานการณ์บัญชีถูกลบ **คือกลไกที่ทำให้เด้งออกได้** ไม่ใช่ความพัง
(เทียบเท่า 403 ของ logout ในโหมด supabase ซึ่งเทสต์ยกเว้นไว้อยู่แล้ว)
ส่วน "ยังไม่ได้ล็อกอินเลย" เซิร์ฟเวอร์ตอบ **204** ไม่ใช่ 401 — ไม่งั้นทุกคนที่เปิดหน้าเข้าสู่ระบบจะเห็น error สีแดง

#### ชุดทดสอบต้องล็อกอินผ่านประตูจริง

ทางลัดเดิมคือยัด session ลง `localStorage` ตรง ๆ ซึ่ง cookie httpOnly ไม่อ่าน
มี 4 จุด: `helpers.openAs` · `funcHelpers.loginUI` · `impersonate.spec` · `multi-dealer-stress.spec`
⚠️ **แก้จุดเดียวแล้วรันชุดเต็มเสียเที่ยวหนึ่ง** — ค้นให้ครบก่อนรันเสมอ (`grep localStorage.setItem tests/`)

### ระยะ 5 · เก็บกวาด — เริ่มแล้ว ⏳ (18 ส.ค. 69)

**ลำดับที่ถูกต้อง: สลับก่อน → ใช้จริงสักพัก → ค่อยลบ**

⚠️ `SupabaseAdapter` (980 บรรทัด) คือ **ทางถอยกลับ** ตราบใดที่ยังไม่ลบ การกลับไปโหมดเดิม
ทำได้ด้วยการแก้ค่าตั้งค่าตัวเดียวแล้ว deploy ใหม่ (~3 นาที) พอลบแล้วทางถอยหายไปทันที
จึงต้องรันโหมด `api` บนของจริงจนมั่นใจก่อน แล้วค่อยลบในภายหลัง

ทำไปแล้วในระยะนี้:
- ล้างคำอธิบายในโค้ดที่ตกยุค (`ระยะ 0 — โครงว่าง`, `เฟส B`, `ย้ายครบ 17/18`) ซึ่งอ่านแล้วเข้าใจผิด
- `/api/v1/ping` เปลี่ยนจากรายงาน "ระยะ 0 ยังไม่มีอะไรย้ายมา" เป็นรายชื่อกลุ่มงานที่ backend รองรับจริง
  → ใช้เช็กหลัง deploy ได้ว่าเซิร์ฟเวอร์ที่ขึ้นไปเป็นรุ่นที่ครบ
- `preflight` เดิมบังคับว่าโหมดต้องเป็น `supabase` เท่านั้น — **สลับแล้วจะตกทั้งที่ตั้งถูก**
  แก้ให้รับทั้งสองโหมด และเพิ่มด่านใหม่: **สองแอปต้องเป็นโหมดเดียวกัน**

ยังไม่ทำ (รอสลับของจริงก่อน): ลบ `SupabaseAdapter` · **ไม่ถอด RLS ไม่ว่ากรณีใด** — เกราะชั้นสอง

## 📋 ขั้นตอนสลับของจริงไปโหมด `api`

### ก่อนกด — ตรวจ 3 ข้อ

1. `npm run preflight` ต้องขึ้น ✅ ครบ
2. Supabase → Authentication → URL Configuration → Redirect URLs
   ต้องมีที่อยู่แอปตัวแทนอยู่แล้ว (ใช้อยู่ตั้งแต่โหมดเดิม — ปกติไม่ต้องแก้)
3. ไม่มีใครกำลังใช้งานระบบอยู่ (ทุกคนจะถูกเด้งออกหนึ่งครั้ง ดูด้านล่าง)

### กด

บน Vercel ตั้ง `NEXT_PUBLIC_DATA_SOURCE = api` ที่ **ทั้งสองโปรเจกต์** (สำนักงานใหญ่ + ตัวแทน)
ขอบเขต Production แล้ว **Redeploy ทั้งคู่**

> ⚠️ **แก้ค่าเฉย ๆ ไม่พอ ต้อง deploy ใหม่** — ค่าที่ขึ้นต้นด้วย `NEXT_PUBLIC_` ถูกฝังลงไฟล์ตอน build
> ไม่ได้อ่านตอนรัน ถ้าลืม deploy จะเห็นเป็น "สลับแล้วแต่ไม่มีอะไรเปลี่ยน" ซึ่งไล่หาสาเหตุยากมาก

> ⚠️ **ต้องสลับทั้งสองแอป** — ถ้าคนละโหมด: ใบผ่านเก็บคนละที่ · เข้าระบบแทนตัวแทนไม่ได้ ·
> ลบสาขาแล้วเด้งออกไม่พร้อมกัน (`preflight` มีด่านดักให้แล้ว)

### ตรวจหลัง deploy — 5 ข้อ

| # | ตรวจอะไร | ผลที่ต้องได้ |
|---|---|---|
| 1 | เปิด `https://<สำนักงานใหญ่>/api/v1/ping` | `ports` มี 18 รายการ |
| 2 | เข้าสู่ระบบ แล้วเปิด DevTools → Application → Cookies | มี `pms_at` และช่อง **HttpOnly ต้องติ๊ก** |
| 3 | DevTools → Application → Local Storage | **ต้องไม่มี** คีย์ `sb-…-auth-token` |
| 4 | เปิดหน้าหลักทุกหน้า ทั้งสองฝั่ง | ข้อมูลขึ้นครบ ไม่มีจอเปล่า |
| 5 | กดปุ่ม "เข้าระบบแทนตัวแทน" | เปิดแท็บใหม่แล้วเข้าได้ มีแถบเตือนสีเหลือง |

ข้อ 2 สำคัญที่สุด — **ถ้า HttpOnly ไม่ติ๊ก ทุกอย่างทำงานเหมือนเดิมเป๊ะ ต่างแค่ประตูยังเปิดอยู่**

### ถอยกลับ

ตั้ง `NEXT_PUBLIC_DATA_SOURCE` กลับเป็น `supabase` ทั้งสองโปรเจกต์ แล้ว Redeploy (~3 นาที)
ข้อมูลไม่กระทบเลย — เปลี่ยนแค่ "คำขอเดินทางเส้นไหน" ฐานข้อมูลชุดเดียวกัน

### สิ่งที่จะเกิดขึ้นแน่ ๆ (ไม่ใช่อาการเสีย)

- **ทุกคนที่ค้างอยู่ในระบบถูกเด้งออกหนึ่งครั้ง** — ใบผ่านย้ายที่เก็บ ต้องเข้าสู่ระบบใหม่
- **จำนวนคำขอที่เซิร์ฟเวอร์เพิ่มขึ้น** — สายอัปเดตสดบนแพ็กเกจ Hobby ถูกตัดทุก ~50 วินาที
  ระบบต่อใหม่ให้เองอัตโนมัติ ผู้ใช้ไม่รู้สึก แต่ควรดูโควตาการใช้งานหลังสลับ 1–2 วัน
