# ผลทดสอบความปลอดภัย — 31 ก.ค. 2569

ทดสอบกับ HQ dev server จริง (`localhost:3002`, endpoint `/api/admin/users`) ไม่มีการสร้างบัญชี/ข้อมูลจริงใดๆ ระหว่างทดสอบ (ยิง body ว่างเปล่าโดยตั้งใจ เพื่อให้ตกที่ขั้น validate หลังผ่าน auth/rate-limit แล้ว)

## 1) ปลอม token (token forgery)
| กรณี | ผลลัพธ์ที่คาด | ผลจริง |
|---|---|---|
| ไม่ส่ง token | ปฏิเสธ | HTTP 401 ✅ |
| string มั่ว | ปฏิเสธ | HTTP 401 ✅ |
| JWT รูปแบบถูกแต่ signature ปลอม | ปฏิเสธ | HTTP 401 ✅ |
| token ว่างเปล่า | ปฏิเสธ | HTTP 401 ✅ |

**สรุป: ผ่าน** — เซิร์ฟเวอร์ตรวจสอบ token ทุกครั้งจริง ไม่มีทางสวมรอยด้วย token ปลอม

## 2) Rate limit (กันยิงรัว)
ยิง POST rัว 13 ครั้งติดต่อกันด้วย token ผู้ดูแลตัวจริง (ผ่าน auth) แต่ body ว่างเปล่า (ไม่สร้างจริง):
- คำขอ #1–10 → HTTP 400 (ผ่าน rate-limit ปกติ ตกที่ validate)
- คำขอ #11–13 → HTTP 429 (โดนบล็อก)

**สรุป: ผ่าน** — ตรงตามที่ตั้งค่าไว้ (จำกัด 10 ครั้ง/นาที ต่อผู้เรียก, ดู `packages/shared/lib/rateLimit.ts`)

## 3) CSRF — ตรวจสอบเชิงสถาปัตยกรรม (ไม่ใช่การยิงโจมตีจริง)
ตรวจโค้ดแล้วยืนยันว่า **ระบบไม่มีช่องโหว่ CSRF แบบดั้งเดิม** เพราะ:
- session เก็บใน `sessionStorage` ของเบราว์เซอร์ ไม่ใช่ cookie (`packages/shared/lib/data/supabase/client.ts`) — เบราว์เซอร์จะไม่แนบให้อัตโนมัติข้ามเว็บไซต์
- ทุก API route (`/api/admin/users`, `/api/admin/dealers`) อ่าน token จาก header `Authorization: Bearer` เท่านั้น ไม่มีจุดไหนอ่านจาก cookie
- หน้าเว็บของผู้โจมตีไม่มีทางอ่าน sessionStorage ของอีก origin ได้ (same-origin policy) และฟอร์ม HTML ธรรมดาก็ตั้งค่า header กำหนดเองแบบนี้ไม่ได้

**สรุป: ไม่เข้าเงื่อนไขที่จะถูกโจมตีแบบ CSRF ได้ตั้งแต่ต้น** (ไม่ใช่แค่ "ยังไม่เจอช่องโหว่")
